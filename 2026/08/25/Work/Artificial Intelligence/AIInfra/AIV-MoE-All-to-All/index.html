AIV MoE All-to-All

导言

MoE 的 All-to-All 不是一次整齐的等长集合通信，而是由路由结果决定长度的 pack、跨 rank 搬运、完成通知、expert 计算、反向搬运与 combine。固定源码表明：TileXR 主仓已经预留 sendCountMatrix、UDMA flag 与设备指针，却没有落地可追踪的 MoE dispatch/combine kernel；真正实现分别位于它固定的 SHMEM fork 和 cann/shmem。本文只描述源码能证明的部分，所有缺少完整实验条件的性能数字均标为未公开或不可归因。

先说结论

三条边界

  1. 能力预留不等于算子实现：TileXR 的类型、注册项、sendCountMatrix 和 DeepEP 设计文档不能证明主仓已有 MoE kernel。
  2. 子模块能力不等于主仓能力：融合 Dispatch-GMM-Combine 样例属于 LingquLab/shmem@b79bda38；classic/doubleplane/MegaMoE 属于 cann/shmem@382afa08。
  3. 端到端提升不等于 AIV 收益：直驱、融合、量化、传输引擎与拓扑会同时改变，缺少消融实验时不能把总收益归给 AIV。
层次 固定 revision 中实际存在的内容 证据边界
概念 MoE route 产生不等长 peer 流量，dispatch 与 combine 构成往返数据交换 通用机制，由 classic/MegaMoE 源码具象化
可复用机制 对称内存、rank -> peer 地址映射、Put/Get、ready/count signal、quiet、barrier cann/shmem@382afa08 有公开实现
TileXR 框架接入 CommArgs::sendCountMatrix、extraFlag::UDMA、udmaInfoPtr、Host InitUDMA 是预留与初始化草稿，不是 MoE 实现
SHMEM 算子样例 classic Dispatch/Combine、双平面、MegaMoE；固定 fork 的融合样例 必须按仓库与 commit 单独归属

UDMA 原语应怎样理解

cann/shmem@382afa08 公开 UDMA Put/Get/Quiet/Atomic/Put+Notify，但其 classic MoE 没有使用这些 UDMA 接口。公开契约要求：

  • Put/Get 是非阻塞提交，Get 结果读取或 Put 源复用前必须 aclshmemx_udma_quiet(pe)；
  • 单请求最多 256 MB，超出需分块；
  • 同一 PE 不支持并发 RMA/AMO；
  • aclshmemx_udma_put_signal_nbi 将数据写与 signal 更新编码为一个 WRITE_WITH_NOTIFY WQE，但返回仍只表示提交。

两个融合变体

TileXR 固定 fork

LingquLab/shmem@b79bda38 的 examples/dispatch_gmm_combine 确实实现融合路径：AIV 执行 Dispatch/Combine，AIC 执行两次 GMM，中间以 cross-core flag 协作。AIC/AIV 分工

Dispatch 先路由和量化，再用 aclshmem_ptr 映射 peer 的 token-count、A 与 per-token scale；Combine 写回 peer D，做跨 rank 同步和 token unpermute。Dispatch/Combine

不是 UDMA 证据

该样例目录没有 aclshmemx_udma_* 调用，真实路径是 aclshmem_ptr + GM-to-GM/MTE。其默认示例是 EP=2, M=64, K=7168, N=4096, E_l=2, TopK=8, maxOutputSize=1024，Host 只循环一次且没有计时，因此只能证明功能路径，不能证明性能提升。

cann/shmem MegaMoE

cann/shmem@382afa08 的 Ascend950 MegaMoE 把 route mask、FP8 量化、跨 rank dispatch、两次 Catlass GEMM、SwiGLU、写回和 Top-K combine 放进一个 Device 流水。主流程

它先把 inbound mask 写入目标 rank，对本地 BF16 token 做 FP8+E8M0 量化；目标 rank 通过 aclshmem_ptr 远端地址 pull 量化 token，建立 routing metadata，再运行两次 expert GEMM。第二次投影后按 metadata 写回源 rank 的 combinedTokens，最后按 routing weights 合并。远端地址

这个版本同时改变 融合、量化、GEMM 实现、AIC/AIV 流水和通信组织。没有同硬件同 shape 的逐项消融时，任何端到端数字都不可单独归因于 AIV。

异常与边界

  1. 无效 expert id：classic dispatch 没有在 kernel 内显式拒绝 expert_id >= P*E_l。无效 route 可能被发送端丢弃，而 combine 仍等待其 status，生产接入必须前置校验。
  2. 无限等待：classic signal wait、固定 fork barrier、MegaMoE generation wait 均无故障超时；peer 失败或状态缺失会挂住。
  3. 容量截断：固定 fork 的 maxOutputSize 和 MegaMoE 的 maxReceivedTokens 会限制接收行数；这是有损容量语义，不是无损 All-to-AllV。
  4. 状态复用：ready/count/status 必须在下一代前清理；generation wait 应比较 >= generation，否则快 rank 跨代会让慢 rank永远等不到相等值。
  5. 对称地址：aclshmem_ptr、UDMA Put/Get/Notify 要求对称分配和一致布局；TileXR IPC peerMems[] 不能自动等价为 SHMEM symmetric memory。
  6. TileXR 清理所有权：TileXRCommDestroy 和析构函数都可能 finalize SHMEM，前者还直接 free udmaInfoPtr，但注释称该指针由 SHMEM 管理；需要统一所有权和失败回滚。
  7. 平台不可混用：doubleplane 暂不支持 Ascend950，MegaMoE 只支持 Ascend950，固定 fork 代码选择 AtlasA2。不同平台结果不能互作 baseline。

可复现实验最小矩阵

同一硬件、节点、链路、版本、rank 映射、shape、dtype 和路由分布下，至少分别比较：Host/设备发起、classic/doubleplane、未融合/融合、BF16/FP8，以及 comm_only、kernel_event、full_op、e2e。只有单变量对照才能归因。

总结

MoE All-to-All 的核心不是一个 API 名字，而是 路由元数据如何编码 peer 与变长段、payload 与 signal 如何保持顺序、接收端如何 compact、expert 结果如何按原 token/Top-K 槽位写回。cann/shmem classic 给出了最清楚的教学实现，固定 fork 与 MegaMoE 展示了进一步的融合和量化流水。

TileXR 当前 revision 则停在另一条边界：Host UDMA 初始化、CommArgs 能力字段和薄封装已经出现，但 ABI 不闭合、没有 MoE 调用方。把这一状态准确写成“能力预留/设计意图”，比把子模块样例或未来设计误报为 TileXR 已实现更重要。
