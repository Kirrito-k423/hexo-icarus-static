先固定问题边界

用户与同事进一步确认，本次关心的 RM/RC 差别是：一个本地 Jetty 能否面向多个远端目标，而不是固定 Jetty 对之间的通信。 下文按这个明确的工程问题分析，不再根据缩写猜需求。所谓“任意目标”，仍以资源建立、远端信息交换及访问权限有效为前提。

更正记录

前版一度将主线改为 Reliability Mechanisms，并撤回端点复用方向；按本次进一步确认，这不符合当前任务。可靠性资料保留在文末作为独立背景。本文也不把下面的通用 UDMA WQE builder 冒充成已经验证开启 RM 的完整实现。

WQE 的远端目标在哪里填

直接看 aclshmemi_udma_fill_sqe_base_ctx()。 它在每次构建 WQE 时，从传入的 remote_mem_info 读取目标字段，而不是等敲 doorbell 时再传目标 rank。完整实现见 shmem_device_udma.hpp:528–555。

代码中的几个术语

  • URMA（Unified Remote Memory Access）：统一远程内存访问的软件接口体系，应用通过它管理资源、提交请求、获取完成结果。
  • RMA（Remote Memory Access）：远端内存访问操作，例如 put/write、get/read；不要只凭相似缩写判断可靠性模式。
  • UDMA（Unified DMA）：本文 Ascend 950 示例的数据搬运后端，SHMEM 用 ACLSHMEM_DATA_OP_UDMA 选择它。
  • SHMEM：提供对称内存、PE 编号、put/get 和同步接口的通信库。

UB 网络中的 UB 是 Unified Bus；Ascend C 的 __ubuf__ / UB scratch 中的 UB 是 Unified Buffer，即核内缓冲区。 两者名称相同，职责不同。

elastic_dispatch 现在怎样发送

这一节固定到你给出的 deepep_ccd 分支提交 19c40e9。它已经是 UDMA 发送路径，后续应先核对它的事务完成、错误处理与接收通知契约。 不需要重新实现 token 的专家归属计算。

先确定谁发、发到哪里

Process()把 AIV 分工为打包、远端发送、本地复制、计数等角色：打包核执行 TokenCopyToBuffer() 和 PublishStageDone()，发送核执行 URMASendToken()。当前 rank 的 token 另走 SelfCopyToken()。

buildRemoteWqeDesc() 将 token 到专家的路由转换成一组传输任务。把原函数的关键地址关系单独写出来，就是：

  • tokenId：本 PE 的输入 token 编号；一个 token 可以被路由给多个专家，因此源地址可以重复。
  • targetExpertOnRank：目标 PE 内的专家编号。
  • slotInExpert：该来源 PE 给这个专家的第几个 token。
  • remoteWindowBase：已经包含接收区前缀、本轮 ping-pong 偏移，以及来源 PE 对应专家区的偏移。
  • tokenCommSize：打包后的通信长度，含数据、元信息及分块标志，不能随意替换成原始 hidden dimension 的字节数。

来源：buildRemoteWqeDesc() 第 332–388 行、GetWindAddrByRankId() 第 693 行、目标窗口表初始化第 2230 行。

用现有 SHMEM API 替代手写 WQE

适合作为功能对照的是：保留专家槽、打包格式、writer 分工，用 aclshmemx_udma_qp_put_nbi 替代整个裸 WQE 提交路径。以下是迁移片段，放在发送核的标量控制路径；它依赖现有对象和分配好的 128 B scratch，没有在 950 上编译或运行验证。

这里有三个故意写得明确的约束：

  • qpForRequest 是本次迁移需要提供的列表，不是仓库现有变量或新 SHMEM API。 可从现有 wqeSqIdx 对两条队列取模取得，但必须把队列选择从 simt_nw_mj_vf 拆出来，不能先调用原函数填裸 WQE，再补调公共 put。
  • 不能原样传 remoteAddr[i] 给公共 put。 GetWindAddrByRankId(peer) 已调用过 aclshmem_ptr，而公共 put 还会对目标执行一次 aclshmem_ptr(dst, peer)。片段用本地窗口加同偏移重建对称指针，前提是各 PE 的窗口布局、来源区划分和轮次一致。地址转换实现
  • 普通 put 内部就会提交。 原来在 WQE 填好之后的 WaitAllStageDone() 必须提前。若要恢复批量提交，可研究 SHMEM 的 defer/submit 重载，但当前契约要求一批使用相同的 PE 和 QP；不能用它跨 rank 拼一个批次；这项约束本身不定义可靠性模式。批量提交契约

这一步减少了业务 kernel 对 WQE 字段的依赖，但每条都 quiet 会改变原有重叠与吞吐，只适合作为最初的正确性对照。后续应按独占 QP 管理批次和完成，避免把基线性能当成库或可靠性机制的性能上限。

对当前业务，更稳妥的核对顺序是：

  1. 保留已有专家槽和每 PE 两 QP 的分工，先确认 Host 创建资源时选择的事务/传输服务及完成策略。

  4. 对齐这些接口后再修改 kernel，不能从白皮书里的抽象机制直接猜测一个 WQE bit。

Ascend C 代码怎样写

Host 准备什么

Host 可以理解为 CPU 侧程序，Device 是 NPU 侧 kernel。AIV 是 NPU 的向量计算核；GM（Global Memory）是设备全局内存，通常落在 HBM 上。先沿着官方 main.cpp 读这条顺序：

  1. aclInit、aclrtSetDevice、aclrtCreateStream：初始化运行时，选择设备，创建执行流。
  2. test_set_attr：准备 PE 总数、当前 PE、引导地址和堆大小。这是示例辅助函数，不是 SHMEM 公共 API。
  3. 设置 ACLSHMEM_DATA_OP_UDMA，调用 aclshmemx_init_attr：库准备通信资源。
  4. 所有 PE 按相同顺序、相同大小调用 aclshmem_malloc，得到对称内存。
  5. 初始化各自数据，launch kernel，调用 aclrtSynchronizeStream，检查通信异常并校验结果。
  6. 完成通信后释放对称内存，再 aclshmem_finalize，销毁流、复位设备、结束 ACL。

“对称内存”不是“所有卡内容一样”。它表示各 PE 的分配布局满足对应关系，库可以根据本地对称指针 + 目标 PE找到远端对应位置。底层会进行地址转换，不能把本地普通指针直接当作远端实际地址。

在两卡例子里，令 gva 为本地对称缓冲区起点：

  • gva + 0 对应 PE 0 的 64 字节数据槽。
  • gva + 64 对应 PE 1 的 64 字节数据槽。
  • PE 0 把自己的第一个槽复制到 PE 1 的第一个槽；PE 1 反向复制第二个槽。

双方都有完整输出缓冲区，传输复制数据，不会自动合并或求和。 数据源要一直保留到相应通信完成；结果使用完、所有远端访问结束后才能释放整个堆对象。

补充：可靠性与目标选择分别负责什么

这部分回答的是“发出后怎样确认完成”，与前面“同一发送端点能否选择多个目标”是两个维度。保留它，是因为更换队列映射不能破坏 dispatch 的完成和消费协议。

本文核对的是华为《灵衢基础规范》2.0（封面发布日期 2025 年 9 月）第 6.3–6.4、7.3.1 节，以及《基于灵衢的超节点参考架构白皮书》第 4.2.6 节。来源入口：灵衢官方文档；华为原文公开副本：基础规范 2.0、超节点参考架构白皮书。不把这些层次直接映射为 RM/RC 的模式开关。

先想一个更贴近 dispatch 的场景：卡 0 向卡 1 写一个 token。AIV 已经组好 WQE、敲了 doorbell，但这时还不能直接让卡 1 开始计算。需要继续回答三个问题：数据是否送达、远端事务是否执行完成、接收 kernel 何时可以读取。

传输、事务和应用各负责什么

《基础规范》2.0 的第 6.3 节区分了传输层的 RTP、CTP、UTP；第 7.3.1 节单独定义事务可靠性。它们不能与上层 CQE 或应用 ready flag 混为一谈。

层次 需要解决的问题 已核实的机制 对 kernel 的意义
传输层 包是否正确送达 RTP 使用 PSN、传输应答及重传；CTP 联合下层提供可靠传输 不应自行在 AIV 中仿造协议重传
事务层 远端操作是否正确执行 可靠事务通常返回 TAACK、Read Response 或 Atomic Response；有明确例外 “发出请求”和“远端执行完成”是不同阶段
本地完成队列 发送软件怎样获知完成或错误 SHMEM 提交时维护完成计数，quiet 轮询 CQE 必须核对完成状态及其覆盖范围
接收应用 哪些 token 可以交给计算核 应用定义的 flag、signal 或会合协议 本地 CQE 不会自动变成接收方的消费通知

CTP 不能简单理解成“没有可靠性”。 规范第 6.3.2 节给出的实施例把可靠传输卸载给下层：CTP 本身不执行端到端传输重传，利用链路层点对点重传，在合适的链路条件下为事务层提供可靠服务。相对地，RTP 的第 6.4 节规定了端到端 PSN、应答和重传机制。这两条路线有不同开销和适用边界，不能只凭“可靠性机制”四个字就把现有 CTP 改成 RTP。

TAACK 也不能直接等同于 CQE。 前者是事务响应，后者是软件可观察的完成队列条目。规范第 7.3.1 节还规定了响应聚合、借传输应答携带事务状态，以及特定 CTP + ROL 场景省略正常 TAACK 的例外。必须由配套实现解释这些协议行为最终怎样形成 CQE；不是把 cqe=1 就能独立证明某种可靠性模式已开启。

优势与成本要对应具体机制

可靠性机制的价值，是让错误有检测、响应或恢复路径，并给软件明确的完成边界；它不能保证所有故障都能自动恢复。采用较强的端到端跟踪和应答机制，通常需要相应的状态、响应流量和等待；利用下层可靠性则能减少一部分上层开销，但依赖适用拓扑和错误模型。

对 dispatch 最实用的收益，是让“数据已经可以用”有明确依据。可靠传输不会自动带来跨请求顺序，也不会自动保证接收方已消费数据。 编程时仍需分别处理源缓冲区寿命、数据与通知的先后关系，以及多轮复用。

协议中的自动重传还必须考虑操作语义：规范第 7.3.1 节特别讨论 Atomic 响应失败时盲目重发请求可能导致重复加法。因此，kernel 遇到超时后不能不分情况重发整批 token 或原子计数操作。
